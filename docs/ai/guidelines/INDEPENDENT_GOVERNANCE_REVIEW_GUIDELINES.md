# Independent Governance Review Guidelines

## Purpose and independence
Review whether an applied governance amendment is substantively coherent, authorized, scoped, and fit to proceed to the complete Audit. Review is read-only and distinct from Verification. The Reviewer must differ from the proposal preparer, applier, and verifier.

## Review criteria
Inspect the exact proposal and approval, application evidence, independent Verification report, affected Masters and connected Guidelines/Prompts/Requests/Skills/Agents. Determine whether the change implements only approved intent; preserves authority, lifecycle ordering, human decision/approval semantics, product exclusions, the 52-core catalog, seven separately reported mechanism groups, and independence; resolves stated gaps without creating conflicting or unsupported controls; and correctly distinguishes non-Master effectiveness from prospective Master-baseline adoption.

## Outcomes and failure
Report PASS only when all criteria are supported. Report FINDINGS or CANNOT COMPLETE for defects, missing evidence, stale inputs, or unresolved decisions. Do not edit, approve, apply, substitute for Verification, or run the Audit. Preserve rationale and citations; only PASS hands off to the complete Audit.

## Runtime capability and stage invocation
Review requires a fresh, explicit human stage-start instruction after a passing independent Verification result; neither patch approval nor the verifier's handoff alone starts Review. Before review, record current reviewer identity and tool/permission evidence for reading all bound proposal/approval/application/verification records and affected governance sources, SHA-256 and required read-only consistency checks, and publication of this reviewer's own attempt/report/result/evidence in the authorized Work ID scope. Confirm capability only through runtime declarations, permissions, non-mutating reads/hashes/checks, and authorized record publication. Bind input and output identities/fingerprints. If any prerequisite or publication capability is missing, stale, inaccessible, or conflicting, report `CANNOT COMPLETE` and do not hand off as PASS. An Agent definition is not evidence of executable capability.

## Procedural non-mutation when source-write exclusion is unavailable

For Independent Governance Verification and Review, "read-only" remains an absolute conduct restriction: do not write, repair, normalize, or overwrite inputs, evaluated sources, or another actor's records. It does not mean the runtime is technically incapable of writes. A write-capable tool or writable input ACL, by itself, does not disqualify an invocation; it grants no authority to write sources and does not override any external, organizational, or separately approved restriction. Use this procedural assurance mode only when the actor can:

- Before substantive checks, define the bounded evaluated-input set and record a manifest covering its exact paths, presence and expected absences, tracked/untracked and relevant path-set state, byte counts, SHA-256 values, repository state, and applicable permissions. Include all records and cross-document inputs actually relied upon. Do not represent a HEAD-only list as complete input coverage.
- Record the actor-visible ordered operation events used for checks: actor and attempt, operation/tool identity, arguments or safe integrity-bound representation, start/completion ordering where available, outcome/errors, and affected/read paths where observable. State unavailable event sources and limits. Do not require an exhaustive trusted OS event stream or claim one exists; do not perform write probes.
- Compare input content and path-set fingerprints before substantive work, at meaningful check boundaries, and immediately before final success publication. Reconcile the final comparison to the exact inputs actually checked, including additions, removals, renames, and relevant index/worktree changes. Checkpoints are observations, not proof against transient writes.
- Record concurrency conditions. Prefer a coordinated no-edit interval when available; otherwise state what concurrency can and cannot be observed. A changed evaluated input invalidates affected conclusions until re-evaluated against a bounded current snapshot; an unexplained or conflicting change is `CANNOT COMPLETE`, not a repair task.
- Exclude only this actor's exact designated attempt/report/result/evidence output paths from input comparisons. Never exclude the whole records root or another actor's records. Validate and flush unpublished `.partial` outputs, publish atomically without overwrite, and read back and hash; publication permission is limited to this actor's scope.
- Distinguish a confirmed unauthorized source/record mutation by this actor (`FINDINGS`) from missing or conflicting scope, operation, concurrency, or fingerprint evidence (`CANNOT COMPLETE`). Stop without repair, rollback, or success-shaped output.

A PASS under this mode must identify it as procedural, state event and concurrency coverage/limitations, and disclose that matching endpoint fingerprints cannot prove absence of a transient write or same-principal tampering. It must not claim enforced read-only access, equivalent prevention, or guaranteed security. The exact proposal and Human Approval must expressly acknowledge these material residual risks. This rule does not create a separate generic risk-acceptance stage or weaken any other approved security control.
